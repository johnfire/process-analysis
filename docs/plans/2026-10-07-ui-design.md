# Web UI — design

Agreed 2026-10-07. Supersedes the "v0 is headless" stance in ARCHITECTURE.md for everything except
the analyzer itself, which stays a pure, headless package.

## Purpose

Turn the analyzer into a hosted tool for streamlining client processes: see the findings
(viewer), run the pipeline without a terminal (workbench), and later interview real respondents
(interviews). One user (Chris) for now; invite-only, built so open signup can be switched on later.

## Decisions

| Topic | Decision | Why |
| --- | --- | --- |
| Hosting | Hosted on the VPS, `https://process-analysis.christopherrehm.de` | Client-server first; a local app can come later |
| Stack | FastAPI + Jinja + htmx, SVG drawn in Python | Least code, matches engcrm/gencrm, analyzer called directly |
| Storage | Postgres (own `postgres:17-alpine` container in this app's compose stack) | Chris's choice; per-app DB isolates failures, matching the VPS pattern |
| Seed corpus | Stays as files in git; importable into Postgres | CI scoring must be reproducible without a database |
| Model calls | Direct API calls from a worker on the VPS (keys in server env file) | A service must not depend on a laptop or interactive CLI logins |
| Login | App's own accounts: Argon2id, opt-in TOTP 2FA | No dependency on another app's identity server |
| Signup | Invite-only now; open signup is a switch, off | Client data on a public server; no attack surface without purpose |
| Mail | Plain SMTP via `MAIL_*` env, same account as flashkarte | Independent of notes-world's mail service |
| Deploy | GitHub Actions → ghcr.io image → SSH → `docker compose up -d` → migrate → `/health`; host Apache vhost + Let's Encrypt | The VPS house pattern |

## Architecture

```
Browser ──HTTPS──> Apache (host, Let's Encrypt)
                     └─> 127.0.0.1:81xx ──> process-analysis compose stack
                                              ├─ web     FastAPI + Jinja + htmx
                                              ├─ worker  job runner (model calls)
                                              ├─ db      postgres:17-alpine
                                              └─ backup  postgres-backup-local
```

- **web** serves pages and does no slow work; long work is enqueued in a `jobs` table.
- **worker** claims jobs from Postgres one at a time, calls model APIs, records progress and
  per-job cost, and stops at a cost cap. A dead worker leaves the site up; jobs wait.
- **analyzer/** stays pure. Imported by web, worker, the `pa` CLI and CI. A storage layer loads
  claims from files (seed, tests) or Postgres (app).
- **Schema:** `users`, `sessions`, `invites`, `password_resets`, `recovery_codes`, `audit_log`;
  `clients` → `processes` → `transcripts` → `claims`; `jobs`, `results`. Everything under a client
  is `ON DELETE CASCADE`.

## Screens

Public
1. **Landing** `/` — the premise (22 days, 17 minutes of work) and the sliver-of-work image; a
   **Log in** button opens the login modal.
2. **Login modal** — email, password with show/hide eye toggle, "Forgot password?", error
   message, and a 2FA-code step only for users who enabled 2FA.
3. **Reset** and **invite-accept** pages — targets of the emailed links; set a new password.

Signed in

4. **Clients** `/clients` — list and "New client". Synthetic processes live under a built-in
   "Synthetic corpus" client.
5. **Client** `/clients/<id>` — processes with status (`draft`, `extracting`, `analysed`,
   `failed`) and headline numbers; two-step "delete client".
6. **Process viewer** `/processes/<id>`, tabs:
   - **Timeline** — the time-scale SVG: work solid, internal wait grey, external wait hatched,
     one honest axis; headline cycle efficiency.
   - **Delay** — delay ranking beside complaint ranking with connecting lines.
   - **Cadences** — rhythms that make work wait.
   - **Fractures** — cards with both quotes; click opens the transcript at the line.
   - **Evidence** — every claim, filterable, linked to its quote.
   - **Score** — synthetic processes only.

   **Rule:** a person or cadence with no time evidence is shown as *no evidence*, never as a
   zero-length bar.
7. **Workbench** `/processes/new` — generate synthetic (domain, headcount, sector, cost estimate
   up front) or upload transcripts. **Job page** with live progress over SSE, cost so far, cancel.
8. **Settings** — password, email, 2FA (with recovery codes), data export, two-step account
   delete. **Invites** — send and list pending.

## Accounts

- Passwords: Argon2id. Never retrievable; "forgot password" emails a single-use link expiring in
  ~30 min. The response is always "if that address exists, we sent a link".
- 2FA: TOTP, off by default, enabled in settings; one-time recovery codes.
- First user created by a one-time server command; others by invite.
- Login rate limiting and lockout, `Secure`/`HttpOnly`/`SameSite` session cookies, audit log.

## Data flow

1. Upload transcripts → stored verbatim.
2. **Extract** job → claims via model API; each claim's quote is checked against the transcript
   and rejected if absent.
3. **Analyse** job → pure analyzer → `results` row tagged with analyzer version and model, never
   overwriting earlier results.
4. The viewer reads `results` only; it never runs the analyzer on page load.

## Error handling

- Model call fails → retry with backoff; failure is per transcript, not per job (partial results
  are shown as such, with retry).
- Cost cap hit → job stops cleanly, keeps finished work, status `stopped: cost cap`.
- Worker dies → job heartbeat; stale jobs are marked failed on worker start and can be resumed.
- Analyzer raises → job fails with the message shown; previous results stay visible.
- Delete during a running job → worker checks the job still exists before each write.
- Correlation ID on every request, propagated through job, worker and model call.
- Audit log: logins, failed logins, password/2FA changes, invites, client deletes, job
  start/cancel — actor, action, target, outcome. AI actions are attributed to the model, not
  "system".

## Testing

- Existing 73 unit tests and the scorer stay untouched and run in CI without a database.
- **Unit:** hashing, TOTP, recovery codes, tokens (single use, expiry, tampering), rate limiter,
  cost accounting, SVG output, the no-evidence rule.
- **Integration (real Postgres in CI):** cascade delete leaves zero rows in every table; job queue
  claim/heartbeat/stale recovery/no double-claim; file vs Postgres storage gives identical
  analyzer output.
- **E2E (Playwright):** invite → login; show password; forgot password via a mail sink; 2FA with
  code and with recovery code; seed process viewer tabs render; two-step client delete.
- Model calls replaced by recorded responses in CI; a manual workflow does one live call.
- Post-deploy: `/health` (db, worker heartbeat, migrations) and landing page over HTTPS.

## Build stages

Each stage ends committed, pushed, CI green and live.

0. **CI for what exists** — tests, a score ratchet, lint, typecheck, dependency audit, secret
   scan, Dependabot.
1. **Skeleton live** — compose stack, migrations, `/health`, landing page, deploy workflow, Apache
   vhost, certificate. Needs the DNS record `process-analysis A 82.165.32.162`.
2. **Accounts** — everything in *Accounts* above, with e2e tests.
3. **Viewer** — schema, storage layer, seed import, process viewer.
4. **Workbench** — jobs, worker, API model calls, upload, SSE, cost cap, cancel.
5. **Interviews** — its own design round first (read the engcrm/gencrm interview agents). Before
   any real client data: `gdpr-audit` on the live app and a processing agreement with the client.

The two failing hospital criteria (external share, batch delay) are method work, scheduled
between stages 3 and 4.
